# Gate declarations for this repo -- checked by scripts/check_gate_typing.py
# and documented in docs/GATE_TYPING_LAW.md. Read that file first; this one
# is data, not prose.
#
# There are currently NO live gates declared in readout_universe itself
# (the tier discipline in CLAIMS.md / docs/AI_READING_GUIDE.md already
# does the equivalent job for this repo's own claims via executed-run
# citation, not a pass/fail threshold gate). This file exists so that:
#   (a) the format is documented in one real, parseable place, not just
#       prose in the law doc, and
#   (b) any future threshold-style gate added to this repo (or copied
#       into a sibling repo) has a place to declare its type honestly
#       before it ships.
#
# FORMAT (plain text, no YAML/JSON dependency -- see the parser docstring
# in scripts/check_gate_typing.py for the exact rules; this is round 3 of
# the format, after two adversarial-review rounds found real holes in
# rounds 1 and 2):
#   - '#' lines are comments, stripped before parsing.
#   - Records are separated by one or more blank lines.
#   - Each record is a block of "key: value" lines.
#   - Required on every record: gate, type, description.
#   - type is exactly "P" (physical content) or "U" (unit/convention).
#     Default assumption for any gate with no record here at all: Type U
#     (see docs/GATE_TYPING_LAW.md -- the burden is on the claimant).
#   - Type P additionally requires: negative_control_name,
#     negative_control_value, gate_passes_when.
#       * gate_passes_when is the GATE's OWN pass predicate, declared
#         ONCE, as "<operator> <threshold>" -- operator one of
#         >= > <= < == != . Example: "same-ligand Jaccard >= 0.35 passes"
#         declares gate_passes_when: ">= 0.35". There is no separate
#         operator on the control -- the control has only a measured
#         value, and the gate's own predicate (and only the gate's own
#         predicate) is applied to it. This is deliberate: an earlier
#         format let the record declare its OWN operator, which let a
#         record pick whichever operator made its own arithmetic read
#         FAIL regardless of what the gate actually does -- see the
#         worked counter-example below.
#       * negative_control_value and the threshold inside
#         gate_passes_when must both be real, parseable, finite numbers
#         -- not placeholder text, not nan/inf.
#       * negative_control_result is OPTIONAL. If present it is a
#         human-readable annotation cross-checked against the DERIVED
#         result (gate_passes_when applied to negative_control_value) --
#         it is never read to COMPUTE the result. The checker independently
#         evaluates gate_passes_when(negative_control_value) and rejects
#         the record if that evaluates to "the control satisfies the
#         gate", regardless of what any result field claims.
#
# RESIDUAL, UNFIXABLE RISK (named explicitly -- see docs/GATE_TYPING_LAW.md
# for the full statement): the checker can verify that a record is
# internally self-consistent -- that its own gate_passes_when, applied to
# its own negative_control_value, derives to FAIL. It CANNOT verify that
# gate_passes_when itself matches the gate's REAL pass condition as stated
# in the gate's own `description` prose. Someone can still write a
# description that says one thing and a gate_passes_when that says
# another; the arithmetic will be self-consistent and the checker will
# pass it. Catching that mismatch is a human-review obligation: a
# reviewer must confirm the declared gate_passes_when predicate is the
# gate's actual, real pass condition, not merely that the record parses
# and is internally consistent.
#
# WORKED COUNTER-EXAMPLE #1 -- commented out, NOT a live record, and if it
# WERE live it would be REJECTED by the checker (the historically real
# EGFR C797S contact-residue-Jaccard gate from docs/GATE_TYPING_LAW.md,
# which was reported as passing evidence at the time). 0.70 does not fail
# a ">= 0.35" gate no matter what the (optional) result field claims:
#
# gate: egfr_c797s_contact_jaccard_same_ligand
# type: P
# description: same-ligand co-crystal pairs show contact-residue Jaccard >= 0.35
# negative_control_name: different-ligand pair, osimertinib vs brigatinib
# negative_control_value: 0.70
# gate_passes_when: >= 0.35
# negative_control_result: FAIL
#   <- REJECTED: gate_passes_when(0.70) = (0.70 >= 0.35) = True, i.e. this
#      "negative" control actually SATISFIES the gate. This is exactly the
#      fabricated-evidence framing the law exists to stop.
#
# -- the honest record for this same gate is Type U instead (per
# docs/GATE_TYPING_LAW.md Case 1: no pair in the real 10-pair matrix
# failed 0.35, so no valid Type P record can be written for it at all):
#
# gate: egfr_c797s_contact_jaccard_same_ligand
# type: U
# description: same-ligand co-crystal pairs show contact-residue Jaccard >= 0.35 (threshold demonstrated non-discriminating: max observed different-ligand pair 0.70 > min same-ligand pair 0.47; all 10/10 pairs pass regardless of ligand identity)
#
# (Type U records do not need the negative_control_*/gate_passes_when
# fields -- there is nothing to demonstrate a failure of, by construction.)
#
# WORKED COUNTER-EXAMPLE #2 -- the operator-choice attack that round 3 of
# this format closes. A gate genuinely documented as ">= 0.80 passes",
# with a control value that plainly PASSES the real gate (0.95), can no
# longer be smuggled through by declaring a self-serving operator on the
# control -- there is nowhere left in the record to declare one:
#
# gate: score_gate_attack
# type: P
# description: score must be >= 0.80 to pass this gate (high score = pass)
# negative_control_name: attempted attack
# negative_control_value: 0.95
# gate_passes_when: >= 0.80
# negative_control_result: FAIL
#   <- REJECTED: gate_passes_when(0.95) = (0.95 >= 0.80) = True, i.e. the
#      control SATISFIES the gate's own declared predicate. Under the
#      round-2 format (a separately-declared gate_operator on the
#      control) this record could instead have written
#      "gate_operator: <=" and passed, which is the exact hole this
#      redesign removes.
#
# WORKED VALID EXAMPLE -- a hypothetical gate whose control genuinely
# fails, shown only so a reader can see what a checker-ACCEPTED Type P
# record looks like (also commented out -- still not a live record for
# this repo, since no such gate currently exists here):
#
# gate: hypothetical_example_gate
# type: P
# description: hypothetical property X measured >= 0.35 in the target case
# negative_control_name: known case with no property X
# negative_control_value: 0.10
# gate_passes_when: >= 0.35
# negative_control_result: FAIL
#   <- ACCEPTED: gate_passes_when(0.10) = (0.10 >= 0.35) = False, i.e. the
#      control genuinely does not satisfy the gate, consistent with FAIL.
